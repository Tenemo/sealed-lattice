# Security policy

`sealed-lattice` is development software. It has not been independently audited, certified, or approved for production elections. Do not use it for real ballots, ballot secrecy, result authorization, credentials, keys, or other secret material.

## Report a vulnerability

Use GitHub private vulnerability reporting when available. If it is unavailable, open a minimal public issue requesting a private contact path without including exploit details.

Include the affected package version or commit, a minimal reproduction, the expected property, the observed behavior, and whether secret material or private data may have been exposed. Do not attach real election data, private keys, ballots, shares, witnesses, or unpublished exploit material.

## Supported versions

No release is supported for production election use. Security fixes target the active repository and current published package line unless a later release policy states otherwise.

The sole prototype completion and evidence target is an exact `n = 10` roster,
with active Byzantine bound `f = 3`, reconstruction threshold `r = 4`, and
distinct finality and state quorums of seven. Roster and candidate-suite schemas
and formulas cover sizes `3..20`, but every other size is officially unsupported
and has no current parameter-security, integration, or physical-phone claim.

## Correct use

- Import only from the published `sealed-lattice` package root. Private workspace packages, fixtures, and test helpers are unsupported.
- Anchor the manifest and participant roster outside untrusted transcript data. Derive every shared state, finality, and release witness identity exclusively from that roster and exclude the subject participant where the certificate requires it. Witnessing must be performed by other participant clients, never by an external witness, trusted service, or external finalizer.
- Require positive verification of canonical encodings, hashes, roots, signatures, proof families, contexts, and prerequisites. Do not ignore structured refusals or replace them with producer-supplied labels.
- Do not decrypt individual ballots, aggregate scores, ranks, comparisons, evaluator intermediates, or arbitrary ciphertexts.
- Do not expose VSS shares, trustee secret shares, encryption randomness, proof witnesses, proof randomness, decryption witnesses, or local secret state.
- Generate proof-randomness seeds with a platform CSPRNG, keep them private, and never reuse them across distinct proof attempts.
- Use local atomicity, locks, authenticated records, and checkpoints for honest-client integrity, crash repair, and concurrent-use detection only. They do not prove recency, authorize a shared result, or constrain code controlled by a malicious participant.
- Treat missing, mismatched, corrupt, or unauthenticated participant action state as terminal for that participant. Do not install transported state or recreate an empty state under the same action identity. If an older consistent snapshot is restored and produces conflicting behavior, count that participant as faulty at the quorum layer.
- If participant loss leaves an applicable threshold unavailable, abort that action and manually start a new vote with a fresh action context and fresh setup and secret material.
- Do not infer support for a roster size from structural validation or derived thresholds. Only the exact `n = 10` profile is a current completion and evidence target; another size requires its own generated suite and complete review before any support claim.
- Require the complete vote path to run in supported mobile browsers. Do not move a participant operation to a desktop, native helper, server, remote prover, or stronger device.
- Keep phone feasibility measurements outside suite identity and verifier acceptance. Report target variance honestly, optimize material outliers, and reserve supported-phone claims for exact physical-device evidence without treating an arbitrary numerical target as cryptographic invalidity.
- Internal development adapters that accept a caller-managed secret-storage key require uniformly random, platform-protected key material; do not derive it from a password or another low-entropy secret. Keep each runtime-record key inside one accounted live-key lifecycle, and do not substitute this adapter for the root-backed browser foundation.

A compromised participant device has that participant's keys and authority and may disclose its local secrets or send arbitrary messages. Protocol safety can rely only on verified proofs, accepted-board rules, and the `n = 10` prototype profile's bound of at most three active faulty participants; local locks and storage checks do not make a compromised participant honest. Confidentiality of data already present on a compromised device, compromise beyond the modeled fault bound, malicious same-origin code outside the reviewed client, compromised platform key storage, denial of service, and side channels without explicit evidence are outside the package's current security boundary.
